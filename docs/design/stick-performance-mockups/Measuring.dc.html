USB Stick Performance

Replaces the Read-Speed Benchmark on the Library Statistics page. The old benchmark measured one thing (sequential MB/s) and reduced it to an invented score. A DJ player does three different things to a stick, and a stick can be good at one and terrible at another, so this measures the three separately and says what each one means on the player generations people actually own.

What a player does to a stick

  • Streaming: reading an audio file front to back. Even a bad stick manages several MB/s, and a WAV deck needs 0.2 MB/s, so this almost never causes dropouts. It bounds loads of long files and every copy or backup from a computer.
  • Small random reads: a database page here, a waveform block there. This is what browsing feels like on every player: rekordbox's export.pdb is a file of 4 KiB pages built for on-demand reads by low-power devices, and OneLibrary and Engine OS are SQLite files read in place. Old flash controllers are 4–5× slower here than current sticks, and a worn one far worse, while looking similar on streaming.
  • Small file open + read: one analysis file per track load, thousands of tiny files in a full scan. Directory lookup on FAT32 is a linear search of the folder's entries, so libraries with very large folders pay extra.

One badge per player generation, computed from the measurement that generation depends on. What changes in the code

  • StickSpeedBenchmark grows two measurements and loses score. The comparative score never meant anything to a DJ; the per-generation verdict replaces it.
  • BenchmarkRecord and the local history table gain the two columns. Pre-1.0, so the table is recreated rather than migrated.
  • A new domain type, PlayerAdvisory, holds the generation table and the thresholds, so the QML only renders rows. Testable without a stick.
  • The statistics scan's per-track file_size calls in both readers can use the size the database already stores and only stat when it is zero. Not part of this feature, but it is the biggest read-side cost on a cold stick and was found while looking at this.
  • Everything stays read-only. Opening a SQLite export in WAL mode touches its -shm file; the reader should open with immutable=1 so a "never writes" claim is actually true.
